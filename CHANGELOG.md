# Changelog

Cambios del SDK y notas de comportamiento del API de FiscalAPI que afectan a quien usa el SDK.

## [Sin publicar]

### Cambios incompatibles (BREAKING)

- Se elimina `capitalRegime` de la interfaz `Person` (estaba `@deprecated`): el API no tiene régimen de capital, ignoraba el valor y nunca lo devolvía. En TypeScript, un objeto `Person` que lo incluya o una lectura de `person.capitalRegime` deja de compilar: quite la propiedad de su código y envíe la razón social sin régimen de capital en `legalName`. En JavaScript no hay error, pero el valor nunca tuvo efecto; quítelo también.
- `TaxFile.tin` pasa a ser opcional (`tin?: string`): al subir certificados con `taxFiles.create()` ya no hay que enviarlo (el API usa el RFC de la persona). En TypeScript con `strictNullChecks`, leer `taxFile.tin` da `string | undefined`: el código que lo asigne a un `string` deja de compilar; use `taxFile.tin ?? ''` o compruebe el valor (las respuestas del API siempre lo traen con el RFC de la persona). En JavaScript no cambia nada.
- El API deja de devolver `stripeCustomerId` y `subscriptionStatus` en las personas (`/api/v4/people` y la persona de las reglas de descarga): eran datos internos de Stripe. Este SDK nunca los modeló en `Person`, así que el código tipado con el modelo no cambia; si su integración los lee de la respuesta (por ejemplo, `(person as any).stripeCustomerId` o el JSON crudo), quite esa lectura: el campo ya no llega.

### Modelo `Person`

- Nuevos campos opcionales:
  - `phoneNumber` y `curp`: los aceptan la creación y la actualización de personas.
  - `country`: país de residencia fiscal expandido (solo lectura).
  - `balances`: saldos por tipo de crédito (`CreditBalance`: `creditType` y `available`, solo lectura). Solo aparecen los tipos que la persona ha tenido; un tipo ausente tiene saldo 0.
  - `isOwner`: `true` si la persona es el owner de su tenant (solo lectura).
  - `validTo` (`DateTime | string`, llega como texto ISO 8601): fin de vigencia de la persona (solo lectura). La asigna el API; casi siempre es `null` y es informativa (no limita el timbrado ni el acceso al API).
- `password`: requerida al crear; al actualizar, `null` o vacía conserva la contraseña actual. El API nunca la devuelve.
- `userTypeId`: `"C"` (cliente, el valor por omisión al crear) o `"U"` (usuario). `"T"` (tenant) solo llega en respuestas: el API lo rechaza al crear y al actualizar solo lo acepta si la persona ya es `"T"`.

### Notas del API (sin cambio de forma en el SDK)

- `Person.taxPassword` es la contraseña de la llave privada (.key) que la persona guarda en su perfil; el API no la usa para sellar (al timbrar usa la contraseña de los certificados registrados o la de `taxCredentials`). Solo la reciben con valor la propia persona y el owner del tenant; los demás reciben `null`. Al actualizar, `null` la conserva y `""` la borra.
- En un 400 de validación, cada falla de `data` trae `attemptedValue` (este SDK no lo modela en `ValidationFailure`): el valor de un secreto (contraseñas, códigos, tokens, archivos y contraseñas de CSD/FIEL) llega enmascarado como `"[masked: n]"` (`n` es su longitud), o `"[masked]"` si la falla es de un objeto o una lista que lo contiene.
- `TaxCredential.password` solo se exige en la llave privada (.key); en el certificado (.cer) el API no la usa.
- `TaxFile.tin`: el API ya no lo exige en `taxFiles.create()`; si se omite o va vacío, usa el RFC de la persona. Si se envía, debe ser el RFC de la persona (sin distinguir mayúsculas); si no, el API responde 400 con la falla en `Tin` (después de comprobar que puede gestionar los certificados de la persona; si no, 403). El API no guarda el valor enviado: el `tin` del archivo siempre es el RFC de la persona. En el SDK, `tin` es opcional (ver «Cambios incompatibles»).
- `fileType` (en `TaxFile` y en `TaxCredential`) va como número: `0` = certificado (.cer), `1` = llave privada (.key). El API no acepta el nombre (`"CertificateCsd"`, `"PrivateKeyCsd"`): responde 400. Se corrigen los ejemplos del README que lo enviaban como texto.
- El API ya no devuelve `twoFactorEnabled` en las personas (este SDK nunca lo modeló).
- Las personas ya no traen `stripeCustomerId` ni `subscriptionStatus` (datos internos de Stripe). `validTo` y `committedBalance` son de solo lectura: el API los ignora al crear o actualizar. `committedBalance` es un campo heredado que el API ya no calcula y siempre vale 0; para el saldo use `availableBalance`, `availableValidationBalance` o `balances`.
- Personas: `persons.create()` y `persons.update()` con un correo que ya pertenece a otra persona, de esta o de otra cuenta (se compara sin distinguir mayúsculas ni los espacios de los extremos), responden 400 de validación con la falla en `Email` y el mensaje `The email is already registered.` (en el SDK, `succeeded` es `false`, `message` vale `"The email is already registered."` y `details` trae las fallas como JSON). Antes respondía otro 400 (una falla de Identity o el genérico `A record with the same unique values already exists.`). Al actualizar, el correo actual de la persona no cuenta como repetido. El API guarda el correo sin los espacios de los extremos.
- Personas: `persons.update()` y `persons.delete()` pueden responder 409 con `details` `The person was modified by another request (for example, a failed sign-in). Reload it and try again.` (en el SDK, `httpStatusCode` 409 y `details` trae el cuerpo de la respuesta como JSON, con ese texto en su campo `details`) si otra petición modificó a la persona mientras se procesaba: cuenta cualquier escritura a la persona, por ejemplo un inicio de sesión con su correo (exitoso o fallido) o un cambio en su suscripción. No se guarda nada: vuelva a consultar la persona y repita la llamada. Antes la escritura se guardaba igual y podía deshacer el cambio de la otra petición (el bloqueo de la cuenta por intentos fallidos o la sesión recién iniciada). `PATCH /api/v4/people/{id}`, que este SDK no usa, responde el mismo 409.
- Personas: si `persons.create()` falla en una validación de Identity que el API no revisa antes (por ejemplo, un correo con `ñ` o acentos, que Identity no admite en el nombre de usuario), la falla de validación trae en `propertyName` el campo del request (`Email` o `Password`) y el código de Identity en `errorCode` (p. ej. `InvalidUserName`); antes `propertyName` traía el código (en el SDK, cambia el `propertyName` de la falla que llega en `details`).
- Facturas (`invoices.create()`): con una moneda extranjera (`currencyCode` distinto de `MXN` y de `XXX`), `exchangeRate` 0 o negativo responde 400 de validación con la falla en `ExchangeRate` y el mensaje `If the currency is different from MXN, you must specify the exchange rate of the day of the transaction.` (en el SDK, `succeeded` es `false` y `details` trae las fallas como JSON); antes pasaba la validación del API. Con `MXN` sigue siendo exactamente 1. El complemento de pagos sigue la misma regla en el tipo de cambio del pago (`complement.payment.exchangeRate` frente a `complement.payment.currencyCode`): con `MXN`, exactamente 1 (si se omite, el API usa 1); con otra moneda, mayor que 0. Si no, responde 400 de validación con la falla en `Complement.Payment.ExchangeRate` (mensaje `If the currency is MXN, you must specify the exchange rate equal to 1` o el de moneda extranjera); antes llegaba al PAC, que lo rechazaba, o el pago salía con totales en 0.
- Cambios del API en los endpoints de cuenta, que este SDK no usa (se autentica con API key), así que no le afectan: `POST /api/v4/account/register` y `POST /api/v4/account/info` con un correo que ya pertenece a otra persona responden 400 de validación con la falla en `Email` (`NewEmail` en `info`) y el mensaje `The email is already registered.`; `POST /api/v4/account/change-password` con la contraseña actual incorrecta responde 400 de validación con la falla en `CurrentPassword` (`errorCode` `PasswordMismatch`, mensaje `Incorrect password.`); en general, las fallas que vienen de Identity en `account/change-password`, `account/info`, `account/reset-password` y `account/confirm-email` traen en `propertyName` el campo del request que las causó (`CurrentPassword`, `NewPassword`, `NewEmail`, `ResetCode` o `Code`) y el código de Identity en `errorCode` (`PasswordMismatch`, `InvalidToken`, …), en lugar del código como `propertyName`; `POST /api/v4/account/refresh` con un refresh token vencido responde 401 `Invalid refresh token` en lugar de emitir otro (con uno vigente devuelve el mismo token), así que una sesión iniciada con `account/login` solo se puede renovar hasta 7 días después del login.
